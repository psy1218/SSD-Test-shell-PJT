# 성능 측정 방법과 해석

## 측정 목적

이 실험은 실제 SSD 성능이 아니라 파일 기반 가상 SSD와 테스트 자동화 구조의
비용을 측정한다. 특히 매 명령마다 프로세스를 생성하는 기준 구조와 동일
프로세스에서 저장 API를 호출하는 실험 구조를 비교한다.

## 측정 환경과 조건

- 환경: Ubuntu 24.04.4 LTS on WSL2
- 저장 경로: Windows `/mnt/c` 마운트
- 컴파일러: GCC 13.3.0, `-O2`
- 시계: `clock_gettime(CLOCK_MONOTONIC, ...)`
- 반복: 항목별 5회
- 단위: milliseconds
- 각 반복은 임시 디렉터리에서 수행

## 측정 항목

- 별도 SSD 프로세스 Write 100회
- 별도 SSD 프로세스 Read 100회
- 동일 프로세스 저장 API Write 100회
- 동일 프로세스 저장 API Read 100회
- TestApp1
- TestApp2
- 전체 9개 자동 테스트

프로세스 Read는 SSD 실행과 `result.txt` 원자적 기록을 포함한다. 직접 Read는
저장 API가 NAND를 로드하고 값을 반환하는 시간만 포함하므로 두 값의 비율을
순수한 `fork/exec` 비용으로만 해석해서는 안 된다.

## 분석

Write는 두 방식 모두 매 요청마다 400바이트 전체 이미지와 `fsync()`를 수행해
프로세스 외에도 동기 저장 비용이 지배적이다. Read는 직접 API가 작은 파일을
읽는 반면 프로세스 방식은 `fork/exec/wait`, NAND 로드, `result.txt` 쓰기와
동기화를 수행해 차이가 크다.

최대값이 중앙값보다 크게 나타난 것은 WSL과 Windows 마운트 파일시스템의
스케줄링·동기화 변동 영향을 받은 것으로 추정한다. 따라서 평균만 보지 않고
중앙값과 범위를 함께 기록한다.

## 개선 방향

- 대량 검증 전용 batch 인터페이스로 프로세스 생성 횟수 감소
- Read 결과를 파일 대신 pipe로 전달하는 실험
- 여러 Write를 메모리에 모은 뒤 명시적 flush 수행
- Linux 네이티브 파일시스템에서 동일 실험 재수행

기본 프로젝트 계약은 명령당 독립 SSD 프로세스이므로 위 최적화는 기준 구현에
적용하지 않는다. 검증 구조를 바꾸는 최적화는 별도 실험으로 분리해야 한다.
