# 시연 및 면접 설명 가이드

## 5분 시연 순서

1. `make`로 `ssd`, `testshell`을 빌드한다.
2. `./ssd W 3 0x12345678`과 `./ssd R 3`으로 영속성을 보여준다.
3. `./testshell`에서 `read 3`, `fullwrite`, `fullread` 흐름을 보여준다.
4. `./testshell --run-test TC-F003`으로 독립 Oracle의 Overwrite 검증을 실행한다.
5. `make fault-test`로 두 의도적 결함이 검출되고 정상 SSD가 회귀 PASS함을 보여준다.
6. `sh scripts/run_all_tests.sh`의 `QUALITY GATE PASS`와 GitHub Actions를 확인한다.

## 핵심 질문과 답변 요점

### SSD와 Test Shell을 왜 분리했는가?

실제 사용자 경계인 CLI, 프로세스 종료 코드, 파일 계약까지 검증하기 위해서다.
또한 검증기가 SSD 내부 상태를 직접 읽어 정답으로 삼는 결합을 피할 수 있다.

### Little Endian을 어떻게 보장했는가?

CPU의 메모리 표현을 그대로 `fwrite()`하지 않고 32비트 값을 네 바이트로 명시적으로
인코딩·디코딩한다. 따라서 호스트 엔디안과 관계없이 파일 포맷이 같다.

### 재실행해도 데이터가 유지되는 이유는 무엇인가?

모든 값은 정확히 400바이트인 `nand.txt`에 저장된다. 다음 SSD 프로세스는 파일이
있으면 새로 초기화하지 않고 크기를 검증한 뒤 기존 이미지를 로드한다.

### 독립 Oracle이 왜 필요한가?

SSD가 돌려준 값을 다시 기대값으로 사용하면 SSD와 검증기가 동시에 같은 오류를
공유할 수 있다. 테스트 입력으로만 기대 상태를 갱신하고 실제 Read와 비교해야
조용한 데이터 손상을 검출할 수 있다.

### 테스트가 실제 결함을 찾는다는 것을 어떻게 증명했는가?

LBA 99 쓰기를 버리는 빌드와 기존 값을 덮어쓰지 않는 빌드를 따로 만들었다.
두 바이너리는 성공 종료하지만 지정 테스트가 기대값/실제값 불일치로 FAIL한다.
Mutation Score는 실제 실행 기준 2/2다.

### 오류를 어떻게 재현하는가?

로그에 Test ID, 요구사항 ID, SSD 경로, 명령, 기대값, 실제값, 종료 코드, 시간,
실패 이유를 기록한다. `logs/defect_report.md`에는 결함별 단일 재현 명령과 정상
회귀 결과를 함께 남긴다.

### 회귀 테스트는 어떻게 수행하는가?

일반 테스트, Sanitizer, 결함 검출, 정상 SSD Oracle, 정적 분석을 한 스크립트로
고정했다. GitHub Actions도 같은 스크립트를 실행하므로 로컬과 CI 판정 기준이 같다.

### 성능 수치는 무엇을 의미하는가?

`CLOCK_MONOTONIC`으로 파일 시뮬레이터의 프로세스 방식과 직접 API 방식을 5회
측정한 값이다. 실제 SSD 성능이 아니며 `fork/exec`, NAND/result 파일 I/O,
동기화 비용을 포함한다.

### 실제 상용 SSD 검증과 무엇이 다른가?

실물 장치, NVMe 명령, NAND 물리 구조, ECC, 전원 차단, 장시간 스트레스,
온도·수명 시험이 없다. 대신 요구사항 추적, Oracle, 자동 판정, 결함 주입,
재현 로그, 회귀와 CI라는 검증 소프트웨어 흐름에 초점을 맞췄다.

## 과장하지 않아야 할 표현

- “실제 SSD 성능을 측정했다”가 아니라 “파일 기반 SSD 시뮬레이터 비용을 측정했다.”
- “모든 결함을 찾는다”가 아니라 “주입한 두 결함을 모두 검출했다.”
- “전원 장애에 안전하다”가 아니라 “임시 파일 교체로 손상 가능성을 낮췄다.”
- “상용 SSD 펌웨어를 구현했다”가 아니라 “SSD 검증 자동화 흐름을 재현했다.”
